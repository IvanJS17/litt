# Interface languages (i18n)

LiTT's interface speaks Mexican Spanish (`es-MX`, the default) and English
(`en-US`). The web app uses `next-intl`; the Word add-in uses `use-intl`
with the same catalog. This page is how to write and move interface text. The
catalog package itself is described in
[`packages/i18n/README.md`](../packages/i18n/README.md); the weekly upstream
merge recipe is in
[`UPSTREAM_POLICY.md`](UPSTREAM_POLICY.md#interface-text-from-upstream).

## The pieces

| Piece | What it does |
| --- | --- |
| `packages/i18n/messages/en-US.json` | The source catalog. English **exactly as upstream writes it**, never edited for style, so an upstream text change is a copy. |
| `packages/i18n/messages/es-MX.json` | The same keys and ICU arguments, in Spanish. |
| `packages/i18n/GLOSSARY.md` | How recurring terms are translated. |
| `packages/i18n/src/catalog.test.ts` | Fails when the catalogs differ in keys, arguments, plural or select shape, or when a message still carries the pending mark `⟦por traducir⟧`. |
| `frontend/src/__tests__/i18nLiterals.test.ts` and `i18n-literal-baseline.json` | The literal guard: in the paths listed in `migrated`, visible text must come from the catalog. `allowed` counts, per file, the literals a card could not move yet; the count may only go down. |
| `scripts/i18n/literals.mjs` | What counts as visible text. The guard and the codemod share it. |
| `scripts/i18n/extract.mjs` | The codemod that moves a file's visible text to the catalog. |

Tests render in `en-US` (Vitest wraps `render` with an `en-US` provider and
Playwright sets `locale: "en-US"`), so upstream's English assertions keep
passing. Only i18n-specific tests use `es-MX`.

## Keys

- A key is `<namespace>.<name>`, for example `settings.appearance.title`. The
  namespace is the area: one top-level namespace per area (`common`, `auth`,
  `errors`, `settings`, `training`, ...) and a second level per screen or
  component when the area is large.
- Each card writes only under its own namespace, so parallel cards do not edit
  the same lines of the catalog. The codemod keeps both catalogs with sorted
  keys.
- Use the full key in code: `const t = useTranslations(); t("settings.appearance.title")`.
  Full keys can be searched for, and `next-intl` checks them against
  `en-US.json` at typecheck time (`frontend/src/i18n/next-intl.d.ts`).
  A namespaced translator (`useTranslations("common.meta")`) is fine in
  hand-written code, but the codemod does not mix with it (see below).
- The codemod names a key after its text (`Search files…` →
  `searchFiles`). Rename it to something shorter when the text is long; the
  codemod reuses any key whose source text matches, whatever its name.
- A key that both the web app and the add-in use exists once.
- Messages are ICU: `{name}` for a value, `{count, plural, one {# file} other {# files}}`
  for a count, `{role, select, owner {...} other {...}}` for a choice. Never
  build a sentence from pieces (`"Couldn't " + action`); give the whole
  sentence one message with arguments.
- Dates, numbers and currency go through `useFormatter()` (or
  `createFormatter` outside React), never `toLocaleString` with a fixed locale.
  Times are shown in `America/Mexico_City`.

## The Word add-in

The task pane wraps the app in `LocaleProvider`
(`word-addin/src/taskpane/i18n/`), which holds a `use-intl` provider whose
locale changes without reloading the pane, and points `@mike/client`'s plain
functions at the same locale and catalog (`configureClientLocale`). Its
language comes from, in order:

1. the profile's `uiLocale` (`useProfileLocale`, read once the session is
   known; `null` means "not chosen");
2. the language picked on this device (`localStorage` key `litt.locale`),
   written by the selector on the login screen and in Settings;
3. Word's `Office.context.displayLanguage`, mapped with `negotiateLocale` (any
   `es-*` is `es-MX`, any `en-*` is `en-US`);
4. `es-MX`.

Write add-in text under the `word` namespace with `useTranslations()`;
outside React use `clientTranslator()` from `@mike/client` (the OAuth dialog
and the notices do). In plain functions, `reportFault`/`notifyError` options
(`action`, `fallback`) and anything built at module scope, call
`clientTranslator()(...)` at the moment of use, never a `t` captured earlier,
so a language switch is followed without a reload. A table of labels is a
function of `t`, not a constant. Text that goes back to the model as a tool
result (`useWordAssistantChat`) stays English and is counted in `allowed`.
The add-in's `useTranslations()` is not typed against the catalog;
`frontend/src/wordAddin/wordKeys.test.ts` checks that every literal `t("word.…")`
exists. Specs that run in `es-MX` select by `data-testid`
(`header-menu`, `header-section-*`, `chat-send`), not by English names. The Playwright Office shim reports `en-US` unless a spec
seeds another `displayLanguage`, so existing specs keep seeing English.

Never decide from a translated label. The frontend lint rule (`no-restricted-syntax`
in `frontend/eslint.config.mjs`) rejects comparing `t(...)`, `tAll(...)` or
`clientTranslator()(...)` with `===`/`!==`, `.includes(t(...))`, and comparing a
`.label` with a string literal: carry an `id` or `value` next to the label and
compare that (menu items and toast actions have an `id`).

## Spanish

- Address the user as **tú** («Guarda tus cambios», «Elige tu idioma»), never
  «usted».
- Use the terms in [`GLOSSARY.md`](../packages/i18n/GLOSSARY.md): `matter` is
  «asunto», `workflow` is «flujo de trabajo», `playbook` stays «playbook», and
  so on. A term changes in the glossary and both catalogs at once.
- Keep each message's arguments, plural categories and `=N` cases; Spanish may
  add `many`. The catalog test checks it.

## Writing the text of Settings

The name and the help text of every tab and section of Settings, and of Ajustes
del despacho, follow these rules. They come from Apple's Human Interface
Guidelines (Writing), Material Design (Writing), GOV.UK content design and the
Nielsen Norman Group's guidance on microcopy. New text from upstream is written
the same way before it is merged ([`settings-map.md`](settings-map.md)). Examples
are `es-MX` first, `en-US` after.

1. **Say what it is for and what it changes, in one sentence.** Who sees it or
   whom it affects goes in a scope label, not in the sentence. «Cambia el nombre
   y el perfil del despacho.» with the labels «Lo ven todos los miembros» and
   «Lo cambian propietarios y administradores» / «Change the firm’s name and
   profile.» with «All members see it» and «Owners and administrators change
   it». The labels are `audienceKeys` of the tab in `settingsMap.ts`.
2. **Speak to the person in the second person.** «tú» in Spanish, «you» in
   English; never «el usuario». «Revisa tu perfil», not «El usuario puede revisar su perfil».
3. **Start with an active verb.** «Elige», «Activa», «Guarda», «Invita». Not
   «Permite elegir…» or «Es posible activar…».
4. **One idea per sentence, and short sentences.** About 20 words at most; if a
   sentence needs a semicolon or a «ya que», split it.
5. **Lead with what matters.** The action or the fact first, the condition after.
   «Tus llaves se usan solo si tu despacho lo permite.» (not «Si tu despacho lo
   permite, tus llaves se usarán…»).
6. **Use the person's words, not the system's.** «llaves», «despacho», «Ajustes»,
   «Quitar», «Borrar» as in the [glossary](../packages/i18n/GLOSSARY.md). No
   «BYOK», «token» (unless the setting is about tokens), «endpoint», «scope» or
   «workspace» («espacio» if it must be named).
7. **Sentence case, never Title Case.** «Mis llaves de IA», «Privacy and data»,
   «Scanned document reading». Capitals only for proper names (LiTT, LandingAI,
   Google Drive).
8. **Name things the same everywhere.** A tab, its heading, its search result and
   the links to it use the same words. Change a name in the map and the glossary together.
9. **A button says the action.** «Guardar tipos», «Agregar llave», «Invitar»; not
   «Aceptar», «OK» or «Enviar». If it destroys, it says so: «Borrar» for forever,
   «Quitar» for taking something away (glossary).
10. **Say who sees it or whom it affects when it is not just you.** «Solo tú ves
    esto.» «Aplica a todo el despacho.» «Solo propietarios y administradores.»
11. **Say what happens, not how it works inside.** «Tu despacho decide estas
    llaves» (not «La política allow_personal_keys.ai está desactivada»).
12. **Point instead of repeating.** When the other home owns the thing, write a
    link with the destination in the words: «Abre Ajustes del despacho → Llaves
    del despacho». Never copy the form.
13. **A blocked or empty state says why and what to do next.** «Tu despacho no
    permite llaves propias para esto. Pide a un propietario o administrador que
    las cambie.»
14. **No jargon, no exclamation marks, no «por favor», no humour.** Keep the
    calm, professional tone of the product. Numbers as digits, dates through the
    formatter.
15. **Do not rewrite legal text.** The wording that socium-legal wrote
    (`orgSettings.profile.*`, `settings.splitClasses.noClientData`,
    `documents.split.notice*`, the scan reading disclaimer in `settings.scanReading.*`,
    the managed-accounts notice) is changed only by them; a rule here never
    justifies editing it.

16. **A setting shows its name and at most two lines (160 characters).** How
    it works, why, and the links go under «Más información»
    (`SettingsMoreInfo`). Notices of cost, third parties, deadlines and
    irreversibility are never hidden there: they go in a `SettingsNotice` or a
    `SettingsNoticeLine`. A sentence that would repeat on every row goes once,
    above. The legal text of rule 15 may sit inside a `SettingsNotice`, whole
    and unedited.

The six signals of Settings (components in
`frontend/src/app/components/settings/SettingsText.tsx`, one place each):

| Signal | Component | Where |
| --- | --- | --- |
| Optional | `SettingsTag kind="optional"` | next to the section title |
| Recommended | `SettingsTag kind="recommended"` | next to the title; at most one a screen |
| Who it applies to | `SettingsTag kind="audience"` | under the tab's help text (`audienceKeys`) or next to a section title |
| «Lo administra tu despacho» | `SettingsManagedRow` | first row of the card; never a sentence under it |
| Notice (cost, third party, deadline, not verified) | `SettingsNotice` / `SettingsNoticeLine` | inside the card, before the control it is about |
| Irreversible | `SettingsNotice tone="irreversible"` | once, between the title and the group of actions that delete |

No amber and no blue; red only for what cannot be undone.

Where the text lives: the names and help texts of tabs are in the catalogs under
`settings.map.tab.*` (personal) and `settings.map.firmTab.*` (firm), the groups
under `settings.map.group.*`. `en-US.json` is upstream's English for the rest of
the app, but these keys are LiTT's: they are written by these rules, not copied.

## What is not translated

- Legal content: playbooks, rules, EKATE and preset templates, sources and
  provenance.
- AI answers and system prompts. The model keeps answering in the language it
  is written to.
- The user's documents and file names.
- Training text written by mentors or users.
- Model and provider names, and technical values (ids, codes, *Request ID*).
- Raw detail of audit events.
- Enumeration values stored in the database (`professional_title` such as
  `'Partner'`, `practice_setting`, `practice_areas`): only the label shown for
  a value is translated; the stored value and its `check` stay in English.
- Brand names the guard lists as exceptions: LiTT, MikeOSS, Microsoft Word,
  Google Drive, BYOK.

## A new screen

From the moment `next-intl` is in `main`, every new web screen (and every new
add-in screen, now that the add-in has its provider) is written bilingual:

1. Pick the namespace for the screen, for example `training.mentorPanel`.
2. Write the text in `en-US.json` and its translation in `es-MX.json` in the
   same change. Use `t("training.mentorPanel.title")` in the component.
3. Add the screen's path to `migrated` in
   `frontend/src/__tests__/i18n-literal-baseline.json`, with no `allowed`
   entry.
4. Run the catalog and literal tests (below).

It is equally fine to write the screen with English literals and run the
codemod on it before the PR, then translate the pending messages.

## Moving existing text: the codemod

```bash
# Dry run: prints the diff it would make, the new keys and what it left.
node scripts/i18n/extract.mjs --ns history.datePicker frontend/src/app/components/history/HistoryDatePicker.tsx

# Write it: the file, both catalogs and the literal baseline.
node scripts/i18n/extract.mjs --ns history.datePicker --write frontend/src/app/components/history

# A LiTT file whose text is in Spanish: the text goes to es-MX, en-US is marked.
node scripts/i18n/extract.mjs --ns training.settings --from es-MX --write frontend/src/app/components/training/TrainingSettings.tsx

# Drop the namespace's keys that no source names any more.
node scripts/i18n/extract.mjs --ns history.datePicker --prune --write

# Same, when the code builds some keys at run time (see "Dynamic keys").
node scripts/i18n/extract.mjs --ns history.datePicker --prune --allow-dynamic --write
```

Paths are relative to the repository root and may be files or folders (tests,
stories and `.d.ts` files are skipped). It runs on Node 22 and loads
TypeScript 5 from `frontend/node_modules`, so run `npm ci --prefix frontend`
first. If TypeScript is missing, or is not major version 5, it exits with a
message saying so and what to run.

What it does, for every literal the guard flags:

- JSX text becomes `{t("ns.key")}`, a visible attribute (`aria-label`,
  `title`, `placeholder`, `alt`, `label`, ...) becomes `attr={t("ns.key")}`,
  and a string in a visible JSX expression, a `toast`/`notify`-style call or a
  visible object key (`label:`, `title:`, ...) becomes `t("ns.key")`.
- Text next to values in JSX, or a template literal, becomes one message with
  arguments: `Welcome back, {user.name}` → `t("ns.welcomeBackName", { name: user.name })`.
- A count with `n === 1 ? "file" : "files"` becomes a plural:
  `{n, plural, one {# file} other {# files}}`.
- JSX whitespace and HTML entities (`&apos;`, `&hellip;`, ...) are read the
  way React renders them.
- It adds `const t = useTranslations();` at the top of the component or hook
  (`const t = await getTranslations();` in an async server component) and
  the import (`next-intl`; `use-intl` for `word-addin/` and `packages/`).
- It adds each key to the source catalog with the text exactly as written and
  to the other catalog with the mark `⟦por traducir⟧ <text>`. The catalog
  test fails until each marked message is translated.
- It adds the path to `migrated` and sets `allowed` for each file to what it
  left, so the guard passes with an honest count.
- It edits only the literal's own characters, the declaration and the import;
  the rest of the file keeps its formatting.
- It is idempotent: running it again changes nothing.

What it leaves as a literal, and lists with the reason:

- text outside a component or hook (module constants, plain helpers, class
  components): move it by hand, for example by turning the constant into a
  function of `t` or storing keys instead of text;
- a component where `t` is already something else, or a callback in between
  that rebinds `t`;
- text with `{`, `}` or `<`, an unknown HTML entity, two plurals in one
  message, or a value it cannot name (a call such as `${date.toISOString()}`):
  compute the value into a named variable first.

### Dynamic keys and `--prune`

`--prune` finds a key by reading the source for its literal text. It cannot
see a key built at run time, so it warns (on stderr, as `file:line`) about
every call of a translator or a translator hook whose argument is not a
string literal. What counts as a translator call is listed once, in
`TRANSLATORS` in `scripts/i18n/extract.mjs`:

- `t(`, `t.rich(`, `t.markup(`;
- `useTranslations(ns)` and `getTranslations(ns)` when `ns` is not a literal,
  also in the options form `getTranslations({ locale, namespace: ns })`
  (a `namespace` that is not a literal, or an object spread, is dynamic; no
  `namespace` or a literal one is not);
- the translator those hooks return, **whatever the variable is called**
  (`const tr = useTranslations("a"); tr(`k.${x}`)`), also an alias of an
  alias, and a hook imported under another name
  (`import { useTranslations as ut }`);
- the shared factories: `clientTranslator()(`k.${x}`)` and
  `createTranslator({ ... })(...)` (also `.rich`/`.markup` on them), and any
  callee of the form `xxxTranslator(...)(key)`.

To teach it a new hook or factory, add its name to `TRANSLATORS` and to this list.

```text
warning: frontend/src/app/lib/authMessages.ts:37 t(`auth.errors.${sentence}`) is not a literal: --prune cannot see which keys it uses
```

The warning is also printed when a dynamic call is in a file the codemod
extracts. When `--prune` (dry run or `--write`) finds any such call in
`frontend/src`, `word-addin/src` or `packages`, it **refuses**: it lists them,
exits with a non-zero code and changes nothing. Preferred fix: make the keys
literals (a map from the value to a full key, `t("auth.errors.expired")`).

If the dynamic uses are known to be safe, `--prune --allow-dynamic` prunes
anyway but keeps every key a dynamic call may reach:

- `` t(`auth.errors.${x}`) `` and `"auth.errors." + x` keep every key that
  starts with `auth.errors.` (also under a namespaced translator);
- `t(KEY)` with a constant, a variable or a call, and `useTranslations(ns)`
  / `getTranslations({ namespace: ns })` with a variable, say nothing about the key, so they keep **every** key of
  the namespace: nothing is deleted.

**Limits (by design: detection is by name, not by types).** The detector does
not follow a translator through destructuring (`const { tr } = hooks`,
`const [x] = ...`), through a prop or a function argument
(`function Row({ tr }) { tr(`k.${x}`) }`), through a property of an object
(`this.tr(k)`, `ctx.translate(k)`) or through a wrapper under another name.
Such a call is **not** warned about and `--prune` may delete the keys it
uses. Keep such code on `t`, or use literal keys, before pruning a namespace
it touches; review the dry run's `- key` lines against a text search for the
namespace.

After writing, always:

1. translate every `⟦por traducir⟧` message with `translate.mjs --export` and `--apply`
   (see [Translating pending messages](#translating-pending-messages));
2. run `npm run typecheck --prefix frontend`: it rejects a key that is not in
   `en-US.json` and a value `t()` cannot take, such as an element where the
   codemod expected text (use `t.rich` for those);
3. run the catalog and literal tests and the component's own tests.

### Translating pending messages

The codemod leaves each new es-MX message marked `⟦por traducir⟧`. The recipe is
the same for a new screen and for every upstream sync cycle (only the new keys
are pending, so only they are translated). `translate.mjs` calls no model: it
exports the pending messages and validates and saves what comes back.

1. Run the codemod:

   ```bash
   node scripts/i18n/extract.mjs --ns settings.appearance --write frontend/src/app/components/settings/...
   ```

2. Export the pending messages (`--ns` narrows them to a namespace):

   ```bash
   node scripts/i18n/translate.mjs --export /tmp/i18n-pending.json [--ns settings.appearance]
   ```

   The file holds `pending` (key → en-US text, only the marked keys),
   `examples` (40 already translated en-US → es-MX pairs of the catalog, same
   root namespace first, then short messages in key order), and the paths of
   the `glossary` (`packages/i18n/GLOSSARY.md`) and the `rules` (the
   [Spanish](#spanish) section of this document). With nothing pending it says
   so and exits 0.

3. Translate. A subagent or a person does it, following the glossary and the
   rules and imitating the examples, and leaves a flat JSON of `key → es-MX
   text` with the same keys as `pending`. Keep ICU arguments, plural and select
   cases, and tags exactly as in the source; Spanish may add `many`.

4. Apply it; this is where the validation happens:

   ```bash
   node scripts/i18n/translate.mjs --apply /tmp/i18n-translated.json [--receipt <path>]
   ```

   Per key, before anything is written: the key must be pending (an unrequested
   key or one already translated is rejected), the text a non-empty string
   without the mark, valid ICU with the same arguments, tags, plural and select
   shape as its en-US source (`scripts/i18n/icu-compare.mjs`, the same check as
   the catalog test); a literal `\u003c` or `\u003e` is read as `<` or `>`. Only
   the keys that pass are written, in the codemod's own format, so the diff
   holds only the translated messages. The rejected keys are printed with their
   reason, and so are the pending keys the file did not carry. The exit code is
   1 while any key is rejected or still pending. The optional receipt holds
   counts only, never message text.

5. Fix what was rejected or missing in the JSON and run `--apply` again; the
   keys already saved are no longer pending, so repeating it is safe.

6. Run the tests:

   ```bash
   npm test --prefix frontend -- ../packages/i18n ../scripts/i18n
   ```

### A sentence split by an inline element

A sentence that an element interrupts (a link, `<strong>`, `<code>`) is not
two messages. Splitting it into `"Read the "` + link + `" before you
continue."` fixes the word order in English and makes it untranslatable:
Spanish needs the pieces in another order. The codemod cannot do this for
you: it leaves such a run alone or moves each text on its own. Write one
message with tags and let `t.rich` fill them in. For example
`packages/ui/src/SourceCodeLinkUI.tsx` shows «Código fuente» in one text and
«de esta versión (se abre en una pestaña nueva)» in another, inside one link:

```tsx
// Before: two literals, one sentence.
<a href={href}>
    Source code{" "}
    <span className="sr-only">of this version (opens in a new tab)</span>
</a>

// After: one message, the tag marks the part that is not visible.
<a href={href}>
    {t.rich("footer.sourceCode", {
        hidden: (chunks) => <span className="sr-only">{chunks}</span>,
    })}
</a>
```

```json
"footer": {
  "sourceCode": "Source code <hidden>of this version (opens in a new tab)</hidden>"
}
```

`es-MX` keeps the same tag around its own words: `"Código fuente
<hidden>de esta versión (se abre en una pestaña nueva)</hidden>"`. The catalog
test checks that both messages use the same tags. A tag name is any word;
`t.rich` replaces it with the result of the function of that name, which gets
the text between the tags. `t.rich` is also what to use when a value is an
element (a link, an icon) and not text.

```bash
npm test --prefix frontend -- ../packages/i18n src/__tests__/i18nLiterals.test.ts ../scripts/i18n
```
